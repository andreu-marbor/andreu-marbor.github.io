01 · Profile

About me

I work as a Lead Software Engineer and have been building software for around eleven years in enterprise environments. That time is split between backend — Java, Spring, APIs, services and integrations consumed by other teams — and frontend: Java Swing, Angular and TypeScript in client and web applications that also have to keep working five years from now. As a lead, technical leadership — design decisions, review and supporting the team — is part of the day to day.

My main interest is system design: where the boundaries of a domain go, what depends on what, how an architecture evolves without rewriting everything, and what makes a long-lived system maintainable. Working across the different layers, from the API contract to the interface and from the interface to the client, is where I am most at home.

At work I use Codex as part of my daily AI-assisted development, and one of my responsibilities is its adoption across the teams: how to bring AI tools into engineering workflows and move from an individual tool to a team practice. I also hold several official OpenAI certifications. Outside of work I investigate what changes when we stop talking about assistants and start talking about agents: OpenCode, subagents, skills, commands and multi-agent workflows.

API + mobile app · Python and Flutter

CatFoodCheck

When buying cat food you need to know, on the spot, whether the brand meets the WSAVA guidelines; that information lives in third-party databases and is not at hand in the aisle. CatFoodCheck solves it with two pieces: an API that normalises the query and an app that just scans the barcode and shows the result. Two distinct layers, service and client, that have to fit together.

Architecture
The backend is a single endpoint GET /scan/{ean} that proxies Open Pet Food Facts and returns product, brand and whether the brand meets WSAVA. The Flutter app scans the EAN with the camera and consumes that endpoint. The service is deployed on Render.
Decisions
No database: there is no own state to store, because the source of truth is an external service. The backend fits in a 33-line Python file, so the maintenance cost of the MVP is almost nil. The backend URL lives in a single place in the app.
Known limits and the next step

No tests, the WSAVA brand list is a constant in the code and the comparison is a substring match. Before it grows, the next step is testing that logic and moving the list to configuration.

PWA + APK · TypeScript

Tic-tac-toe

A simple game used as a test bed for a complete product end to end: an unbeatable CPU, three languages, an installable PWA and a published APK, backed by tests and CI.

Architecture
TypeScript and Vite, with no framework and no runtime dependencies. The game logic (rules, minimax with alpha-beta pruning, scoring) is separated from the UI, and the i18n is homegrown: flat English keys with es, ca and en files.
Decisions
Neither i18next nor Jest: 28 keys and deterministic tests do not justify two more dependencies. Tests are bundled with esbuild and run on Node, reusing the compiler already in the project. The service worker only registers in production, and Android ships as a Trusted Web Activity generated with Bubblewrap: a single codebase for web and app.
Real incident and AI verification

The first APK opened with a URL bar: assetlinks.json returned a 404 at the domain root. The fix was publishing the Digital Asset Links at the root of the site you are visiting.

500 games of the CPU against a random opponent without losing a single one, minimax against minimax always drawn, and easy-mode games that are expected to lose sometimes. “Unbeatable AI” stops being a claim and becomes a test.

Quiz Historia

History quizzes for secondary and high-school students, meant for real classroom revision: no backend, no accounts and no personal data, with progress stored on the device itself.

Architecture
Content lives in versioned JSON (topics and questions) and goes through its own validator: unique ids, ranges and types checked before start. Selection, correction and shuffling logic is separated from the DOM so it can be tested; jsdom only enters the screen tests.
Status

This site

The portfolio you are reading, and also where a concrete Android platform problem gets solved: hosting assetlinks.json at the domain root so Trusted Web Activities open full screen.

04 · Practice and experimentation

AI-assisted development

What happens to the software development process when AI agents become part of the development team?

At work I use Codex every day: AI-assisted development is part of my professional practice and of my responsibilities, not a recent discovery. One of them is AI adoption across the development teams: how to bring the tools into engineering workflows and move from an individual tool to a team practice. I frame it as an engineering question: which part of the work is worth delegating to an agent, how to review what it produces, what tests must exist before delegating, and which decisions are not delegated.

Outside of work I investigate the jump from assistant to agent: OpenCode and its concepts — coding agents, subagents, skills, commands, agent-driven planning and multi-agent workflows — keeping notes on what works, what does not, and what real impact it has on code quality and maintenance.

What I keep finding: an agent speeds up execution, not responsibility. Design, review and technical judgement remain part of the job.
